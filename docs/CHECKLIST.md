## 🔒 铁律一：FABE 之 F（事实）来源铁律（2026-09-12 用户批评固化）

> 用户原话：「我都说了呀，你连FABE里F都没搞对。后面的ABE全是错的。」

| 层级 | 权威性 | 规则 |
|---|---|---|
| F-1 | **最高** | 用户已明确给出的判断/反馈/结论——**无条件采纳为事实基线**，禁止用我方解读顶替或反驳 |
| F-2 | 次高 | 可核验的真实信息（截图、数据、文档、实测）——核验方法与结论必须与用户判断一致，冲突时**以用户为准**，先自查我方核验是否有误 |
| F-3 | 最低 | 我方推测/解读/记忆——**永不进入 F**；仅可进入 A 作为待验证假设，且必须标注「待核验」 |

**本次违规复盘**：用户反馈⑤已明说「两个符/两个123不科学」→ 属 F-1，本应直接采纳为事实基线；我却拿模糊 OCR 的「截图原样双入口」（F-3）去反驳 F-1，导致 F→A→B→E 全链错误，还让用户重复指出留边圆角、主题色两个同类问题（F-1 早给出，我未对照自验）。

## 🔒 铁律二：问题收敛原则（2026-09-12 用户要求固化）

> 用户原话：「问题只能越来越少，不能一直都有一大堆的新问题出现。这也是最基本的原则和要求，也要固化。」

**目标曲线**：每轮真机反馈问题数必须单调递减，理想态趋近 0。

| 版本轮次 | 反馈问题数 | 同类复发 | 判定 |
|---|---|---|---|
| v0.4.2 第一轮 | 8 | — | 基线 |
| v0.4.4 第二轮 | 8 | 布局类复发（①） | ✗ 未收敛 |
| v0.4.5 第三轮 | 8 | 布局/留边/圆角/主题色复发（①④） | ✗ 未收敛 |
| v0.4.6 本轮 | 3（双入口误判/留边圆角/主题色） | 同上三类 | 已全修，待真机验证 |

**机制（发布门禁，强制）**：
1. **逐项自验**：发版前必须对照「上轮全部反馈 + 用户原话逐字」，逐项自验通过后才允许发布；自验结果写入 CHANGELOG 对应版本条目
2. **回归零容忍**：已修复项若复发 = 上轮修复不合格，禁止简单再修，必须回到根因（F 是否搞对、验收标准是否钉死）重做
3. **新问题分类**：每轮新问题必须标注「回归 / 新增 / 衍生」，回归问题数计入不合格
4. **F-1 优先**：凡用户明确给出判断的，直接作为验收标准写进版本目标，先做该项再做其他
5. **双平台发布（v0.5.1 固化）**：每个版本必须同时发布 GitHub Release + Gitee Release（tag 与 APK 资产双端齐全），GitHub 用 Actions 产物，Gitee 用 API 上传（token：Gitee 个人访问令牌）；Gitee 服务器匿名访问有 IP 风控（403），用户端浏览器登录后下载不受影响；发布检查单：GitHub tag ✓ GitHub APK ✓ Gitee tag ✓ Gitee APK ✓
6. **Gitee 仓库必须公开（v0.5.2 固化）**：Sync to Gitee 工作流建的镜像仓可能默认为私有（private=True），导致匿名/开源共建者无法访问——任何仓库（client/gateway/rules/ai）在 Gitee 上必须为公开；发布检查单追加：Gitee private=False ✓（API 验证：GET /repos/{owner}/{repo} 的 private 字段）；改公开命令：PATCH /repos/{owner}/{repo}?access_token=…&name={repo}&private=false
